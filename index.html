End-to-End Cryptographic Flow

1
In-Browser Key Generation
Client generates 256-bit AES key using standard window.crypto.subtle.generateKey.
2
Client-Side AES-256-GCM Encryption
Browser generates unique 12-byte CSPRNG IV and encrypts payload. Plaintext never leaves browser memory.
3
Ciphertext-Only Server Transmission
Only scrambled ciphertext + IV are sent to server via HTTPS. The decryption key is NEVER sent.
4
RFC 3986 URL Hash Key Placement
The decryption key is placed after the # character. Browsers NEVER send hash fragments in HTTP request headers.
5
Atomic Read-and-Delete Operation
When recipient requests the secret, SQLite executes BEGIN IMMEDIATE, decrements views, and deletes the row in a single atomic transaction.
6
Client-Side Decryption & Auto-Wipe
Recipient decrypts locally. window.history.replaceState scrubs the key from browser history, and memory shreds after 30s.

Threat Model Breakdown

Clear, honest distinction between what the server learns and what it physically cannot learn.

✓ Server CANNOT Learn
  • • Plaintext message contents
  • • Decryption key (isolated in URL hash)
  • • User passphrase or salt-derived keys
  • • Decrypted file attachments
  • • Secret content after single burn view
⚠️ Server Learns (Operational)
  • • Secret ID (random token)
  • • Creation and expiry timestamps
  • • Approximate ciphertext byte length
  • • Client IP address (for rate-limiting)
  • • Remaining view count
